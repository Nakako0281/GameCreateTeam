## 1. 背景と目的

2026-11-23 の運用において、以下の表裏一体となった2つの組織不全が同時に発生した。
1. **例外状態での無相談強行（Under-escalation）**: `origin/main`（PR #37）と `origin/dev` が 5 ファイル競合している状態（2層ブランチ運用の前提崩壊）を検知しながら、`docs/STATE.md` の1行メモを上位規範より優先し、変則の `release/*` ➔ `main` PR #64 およびそれに依存する連鎖 PR #65 を事前合意なしで作成した。
2. **指摘直後の迎合反転（シコファンシー）と丸投げ再発**: 人間からの「なぜ相談しないのか」というプロセスへの質問に対し、再検証や関係ロール協議を行わず即座に結論を180度反転させ、さらに「明文化すべきでしょうか？」と丸投げ返答を再発させた。

なお、**非迎合・再招集ルール自体は当時すでに4箇所の文書に明記されていたにもかかわらず破られた**。この事実から「文章の禁止・厳守を追加するだけでは AI も人間も例外時に逸脱する」と結論づけ、**人間も従業員の一人として組み込まれた組織全体の「共通レール（3層ハーネス）」で客観境界を物理拘束し、常時読み込みルールは逆に純減させる**方針を採択した。

## 2. 人間の3ロール分離と権限境界（RACI）

「人間の意見は鶴の一声にしない（一従業員・一メンバー）」という原則と、「法的責任・契約名義・GitHub マージ権限は自然人である人間にのみ帰属する」という動かせない非対称性を両立させるため、人間の役割を領域別に 3 つへ明確分離する。

- **Hat 1：法的最終責任者（Legal / External Accountable・委任不能）**
  - 憲法（§1〜§2）改定・絶対禁止事項の例外承認・本番公開（`main` マージ）決裁・独自ドメイン/Cloudflare/GA4/GSC/AdSense 名義と費用・法務リスク受容の最終権限。
- **Hat 2：外部実務担当（Human Responsible）**
  - PRマージ操作・外部管理画面設定・記事公開などの実務を `owner:human` Issue 経由で遂行する。
- **Hat 3：チームメンバー（Team Contributor / Consulted・対等な1票）**
  - 企画・UI・技術・優先度への疑問や提案を行う。**ここでは鶴の一声ではない**。AIトップリーダーおよび専門サブエージェント（`01`〜`06`）と同一の客観根拠・一次ソースで採否を決める。

| 意思決定・業務領域 | AI (`00`+`01〜06`) | 人間 Hat 1<br>(法的最終責任者) | 人間 Hat 2<br>(外部実務担当) | 人間 Hat 3<br>(対等メンバー) | 境界原則 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **1. 憲法（§1〜§2）改定・絶対禁止の例外** | **R / C**（起案・`03`監査） | **A**（承認・拒否権） | I | C | AI単独の憲法改定・例外適用禁止 |
| **2. 通常業務の企画・設計・実装・SEO・監査** | **A / R**（業務執行責任） | I（憲法範囲内） | — | **C**（対等な1票） | 根拠優位ならAI案を採用（人間案を却下可） |
| **3. 開発統合（作業ブランチ ➔ `dev` PR）** | **R**（実装・CI通過・Ready） | **A**（最終確認・決裁） | **R**（マージ実行） | C | AI自己マージ禁止・CI全緑必須 |
| **4. 本番リリース（`dev` ➔ `main` PR）** | **R**（準備・監査） | **A**（公開決裁） | **R**（マージ実行） | C | `dev` 検証済み・乖離ゼロ・合意が前提 |
| **5. 外部認証・契約・費用・法務文言・公開作業** | **R**（調査・ドラフト起票） | **A**（名義・法的責任） | **R**（管理画面作業） | C | `owner:human` Issue で管理 |
| **6. 異常系・ルール衝突・ブランチ乖離・矛盾** | **R**（検知・是正案提示） | **A**（例外/是正決裁） | I | C | **fail-closed**：迂回せず停止し4点セット提示 |
| **7. 保安・信頼境界・ハーネス監査（§2/L-12）** | **R + Veto**（`03`/`05`） | **A**（憲法改定権） | — | C | 憲法違反・外部汚染は人間指示でも保留 |

## 3. 意思決定3区分（Fail-Closed：`Tier 3` ➔ `Tier 2` ➔ `Tier 1`）

### Tier 3：差し戻し・異議申し立て（Hold & Object）
1. **§2・法令/規約・信頼境界違反の指示**: `03` / `05` 権限で実装を保留し差し戻す。
2. **過去操作や前提の不整合**: 例）人間の `main` 直マージ等で2層フローが壊れている状態を黙認して迂回せず、是正（`main ➔ dev` 同期等）を要求する。
3. **Hat 3（メンバー）提案の根拠不足**: 一次ソース・定量計測に照らし AI 案を下回る場合、理由と反証を示して採用を見送る。

### Tier 2：事前相談・合意形成（Escalate & Pause / 迷ったらこちらへ倒す）
1. **ブランチ乖離・フロー逸脱**: `origin/main` が `origin/dev` より先行（`main_ahead_by > 0`）、競合あり、未マージ `main` を混ぜた連鎖PR、`main` 宛て変則PR。
2. **規範・メモの矛盾**: 憲法・細則・ADR・`STATE.md` メモ・Issue間で指示が矛盾している。
3. **本番・法的・外部境界**: 未合意の `main` リリース、法務文言（`/privacy`, `/terms`）の実質変更、CSP許可先・信頼境界（L-12）・ブランド・契約/費用の変更。

#### 提案型エスカレーション4点セット（丸投げ質問禁止）
Tier 2 で停止する際は「どうしましょうか？」と投げず、必ず以下 4 点を揃えて提示する（チャット対話時はその場、無人 `/daily-ops` 時は `owner:human` Issue 起票で停止し、無関係かつクリーンな Tier 1 タスクのみ分離実行可）：
1. **検知した事実と衝突している上位規範**
2. **採り得る選択肢の比較（2案以上・副作用とコスト含む）**
3. **AIチームの推奨案と根拠**
4. **人間に確認・決裁してほしい一点**

### Tier 1：AI単独自律実行（Autonomous Execution）
- Tier 2 / Tier 3 に該当せず、通常 `dev` フロー・可逆範囲・前提一致を満たす全タスク。Adaptive Batching（目安 3〜4pt）で停止せず完遂する。

## 4. 反迎合プロトコル・明示的オーバーライド・規範序列

1. **反迎合（論点分離・即時反転禁止・反証義務）**:
   - プロセス批判や疑問（例：「なぜ相談しなかったのか」）を技術案への否定命令と混同しない。
   - 変更を検討する際は、相手案を採用した場合の欠点・リスクを必ず検証し、重要事項は `05` / `03` を再招集したうえで、客観的に上回る場合のみ結論を改める。
2. **Hat 1 明示的オーバーライド記録フォーマット**:
   - AIの合理的な異議申し立て（Tier 3）に対し、人間が **法的最終責任者（Hat 1）としてリスクを受容したうえでオーバーライド** する場合のみ、以下を該当 ADR / Issue / PR へ記録して実行する（法令違反・認証漏洩等の絶対不可事項は対象外）：
     ```text
     [Explicit Override (Hat 1)]
     - 決定者: 人間（法的最終責任者）
     - 対象とAI側の指摘リスク: ...
     - 採択理由と受容されたリスク: ...
     ```
3. **規範の優先順位**:
   - `AGENTS.md（憲法） > .agents/rules/AGENTS.md（細則）≒ docs/ADR/（確定ADR） > .agents/skills/（手順） > docs/STATE.md・Issueメモ`。
   - 下位メモ（`STATE.md` 等）で上位規範（2層ブランチ運用等）を上書きしてはならない。

## 5. 3層ハーネス設計と機械化境界ポリシー（Issue #56 連動）

| 区分 | ハーネスで物理強制できる領域（実装済み） | ハーネスで縛れない限界（最小ルール＋摩擦で支える） |
| :--- | :--- | :--- |
| **対象** | ・**Layer 1 (`.agents/hooks.json`)**: `SessionStart` での `main` 先行/保護ブランチ警告自動注入、`PreToolUse` での `main`/`dev` 直Commit/Push・PR自己マージ `deny`、保護ファイル・`main` マージ・`main` 宛てPR・`--allow-exception` の `force_ask`<br>・**Layer 2 (`scripts/ops_github.mjs`)**: `status` の `branch_sync` 自動計測、`create-pr` の `base=main` / 連鎖PR fail-closed ブロック<br>・**Layer 3 (`.github/workflows/ci.yml` + Rulesets)**: `base_ref=main` 時の `main ⊆ dev`・`head=dev` サーバー検証 | ・チャット文面でのシコファンシー（即座な迎合反転）判定<br>・人間提案とAI案のどちらが根拠で優位かの意味的判定<br>・指示の業務目的上の矛盾の解釈 |

### 機械化境界ポリシー（ルール肥大化防止）
- **機械化すべきもの**: ブランチ状態、CI環境一致、信頼境界の実動作（`ops-github-trust.test.ts`）、料金スキーマ、PII定量ベンチマーク、フック設定実在など**客観検証可能な不変条件**。
- **機械化禁止のもの**: 精神論・態度・議論姿勢に関する語句を正規表現で検査するルールや、形骸化する定型チェックボックスの強制。これらは `AGENTS.md` / `.agents/rules/AGENTS.md` の行数ソフト予算（各90行目安）内で簡潔な原則として維持する。
