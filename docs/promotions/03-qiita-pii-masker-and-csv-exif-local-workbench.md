## はじめに：生成AIやExcel共有の「手元の下ごしらえ」を安全にしたい

実務で ChatGPT・Claude・Gemini に顧客問い合わせの返信案や障害ログの原因分析を頼みたいとき、あるいは社外・他部署から受け取った Shift-JIS の CSV を Excel で文字化けさせずに開きたいとき、一番引っかかるのが **「社外秘データを外部サーバーへ送信せずに下処理できるか」** という点です。

社内のセキュリティ規定上、謎の変換サーバーへファイルをアップロードすることはできませんし、Webページの入力欄全体を監視できる権限を持ったブラウザ拡張機能も導入ハードルが高くなりがちです。

そこで、**生成AIや社外共有前の下ごしらえに特化した、入力データ送信ゼロ・ブラウザ単一タブ完結の実務ワークベンチ「TemotoBox（てもとボックス）」**（Astro SSG + React + TypeScript、ソースコード公開）を開発しました。

- **TemotoBox**: https://temotobox.com/
- **GitHub（ソースコード・テスト公開）**: https://github.com/Nakako0281/GameCreateTeam

本記事では、特に利用頻度の高い2つのツールについて、**日本語特有の正規表現の罠・往復復元のバグ潰し・115件コーパスと `fast-check` による定量テスト・文字化けCSV修復の実装**をまとめます。

## 1. AI入力前・個人情報（PII）自動マスキング＆回答復元の設計

[AI入力前・個人情報(PII)自動マスキング＆回答復元](https://temotobox.com/tools/ai-pii-masker/) は、単なる黒塗りツールではなく **「1. 決定論的な仮名トークン化 ➔ 2. AIに処理依頼 ➔ 3. 同じタブ内で元の固有名詞へ自動復元」** という往復ワークフローを想定しています。

```text
元の文: 株式会社サンプル商事の佐藤太郎様（sato.taro@example.co.jp）から連絡
   │  ブラウザ内メモリで変換（入力データ送信ゼロ）
   ▼
AIへ渡す文: [ORG_1]の[PERSON_1]（[EMAIL_1]）から連絡
   │  ChatGPT / Claude / Gemini で返信案を作成
   ▼
AIの返答: [ORG_1]の[PERSON_1]宛ての返信案です...
   │  同じタブ内の対応辞書で復元（\[PERSON\_1\] や全角 ［PERSON_1］ も対応）
   ▼
復元結果: 株式会社サンプル商事の佐藤太郎様宛ての返信案です...
```

### 実装で踏んだ日本語・記号の4つの落とし穴と対策

単純な正規表現を並べただけでは、実際の日本語業務文で次々と破綻します。実戦とテストコーパス構築の中で踏んだ代表的な課題と修正ポイントは以下の通りです。

#### ① 日本語法人名と助詞「の」・接尾語境界の衝突
- **問題1**: 「株式会社サンプル商事の佐藤太郎様」に対して接頭型法人名パターンがひらがなを貪欲に読むと、「株式会社サンプル商事の佐藤太郎」までが `[ORG_1]` に飲まれ、`[PERSON_1]` が消えてしまいます。
- **問題2**: 逆に末尾の1文字ひらがな助詞（`の`/`は`/`が` 等）を一律で切り落とすと、「有限会社あけぼの工務店」のようなひらがな末尾「の」＋漢字社名（「工務店」「設計」「製作所」等）が「有限会社あけぼ」で切れてしまいます。
- **問題3**: 「株式会社みずほリサーチ間の契約」では、社名直後の「間」「側」「宛」まで漢字連続として吸収されがちです。

**対策**: 助詞ストップ語（`から`/`より`/`について` 等）で境界を止めつつ、`の` の直後が組織接尾語（`工務店`/`設計`/`総研` 等）に一致する場合のみ接続を継続し、逆に末尾の `間`/`側`/`宛`（ただし「時間」「空間」等を除く）の直後に助詞や句読点が続く場合は装飾接尾語としてトリムする境界制御を実装しました。

#### ② PKCS#8 秘密鍵（`-----BEGIN PRIVATE KEY-----`）の取りこぼし
初期パターンでは `-----BEGIN [A-Z0-9 ]+PRIVATE KEY-----` と中間文字列を1文字以上（`+`）要求していたため、`BEGIN RSA PRIVATE KEY` は検出できるのに、現在主流の PKCS#8 形式（`-----BEGIN PRIVATE KEY-----`）を見逃していました。`[A-Z0-9 ]*` へ修正して両形式に対応しています。

#### ③ `restoreMaskedText` のバックスラッシュ食い込みと既存トークン衝突
Property-based test の導入前に静的検証で見つかった、地味ながら往復一致（`restore(mask(x)) === x`）を壊すバグが2つありました。

1. **バックスラッシュ食い込み**: Markdown エスケープ（`\[PERSON\_1\]`）を復元できるよう `(?:\\?\[|［)...(?:\\?\]|］)` としていたため、元文が `\sato@example.com`（マスク後 `\[EMAIL_1]`）のように直前に `\` があるだけの文字列で、復元時に先頭の `\` まで消費して `sato@example.com` に化けていました。**開閉括弧の両方がペアでエスケープされた場合（`\[...\]`）のみ `\` を消費する**パターンへ修正し、元の `\` を保護しました。
2. **元テキスト内の既存トークン文字列との衝突**: 元文にリテラル文字列として `[EMAIL_1]` が既に書かれている状態で別のメールアドレスが登場すると、採番が `[EMAIL_1]` に衝突して復元時に元からあった方まで書き換わってしまいます。マスキング開始時に元文中の既存トークン形式を収集し、採番時にスキップする仕組みを入れました。

#### ④ Luhn 検算と日本語ストップワード
クレジットカード番号候補（13〜19桁）は **Luhn チェックディジット** を通過したものだけを `[CARD_1]` とし、16桁の伝票番号などの誤検知を抑制しています。また「お疲れ様」「お客様」「ご担当者様」「前回同様」「基本仕様」「営業部長」「弊社社長」のような一般表現はストップワードと敬称前後の後読み・接頭辞ルールで除外しています。

## 2. 正規表現の限界を隠さない：115件コーパス定量計測 ＋ `fast-check` ＋ 目視注意表示

正規表現ベースの PII 検出は高速かつオフライン完結できる反面、**「敬称が付かない呼び捨ての個人名（例：`担当：佐藤` や `田中が対応予定`）」などを 100% 機械的に見抜くことは原理的に不可能**です。

そこで TemotoBox では「何でも完璧に隠せます」と過信させるのではなく、以下の3層で信頼性を担保しています。

### ① 115件の実務コーパスによるカテゴリ別 Recall / Precision ベンチマーク（CIゲート化）
メール（25件）・議事録（20件）・問い合わせ（25件）・チャット（20件）・システムログ（10件）・誤検知トラップ集（15件）の計115文書を作成し、マルチセット一致で毎回 CI 計測しています。あえて敬称なしの呼び捨て表記3件も正解に含めたうえでの実測結果は以下の通りです。

| カテゴリ | TP | FP | FN | Recall | Precision | F1 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| APIキー・秘密鍵 (`apiKey`) | 16 | 0 | 0 | 100.0% | 100.0% | 100.0% |
| メールアドレス (`email`) | 32 | 0 | 0 | 100.0% | 100.0% | 100.0% |
| 電話番号 (`phone`) | 25 | 0 | 0 | 100.0% | 100.0% | 100.0% |
| 郵便番号 (`postalCode`) | 14 | 0 | 0 | 100.0% | 100.0% | 100.0% |
| IPv4アドレス (`ipv4`) | 17 | 0 | 0 | 100.0% | 100.0% | 100.0% |
| クレジットカード (`creditCard`) | 7 | 0 | 0 | 100.0% | 100.0% | 100.0% |
| 12桁ID (`myNumber`) | 10 | 0 | 0 | 100.0% | 100.0% | 100.0% |

### ② `fast-check` による往復 Property-Based Testing
5つの性質（ランダム業務文・任意文字列・既存トークン衝突・全角/MarkdownエスケープされたAI応答・`$1`/`$&`/`C++` 等のメタ文字を含むカスタム辞書）を各150回ランダム生成して「マスク ➔ 復元で元の文が壊れないこと」を Vitest 上で検証しています。

### ③ UI上の常時目視確認アナウンス
どれほど精度を上げても「敬称なしの個人名や社内固有の案件名」は漏れる可能性があるため、マスク出力欄の直下に常に目視確認と「カスタム語設定」への追記を促す注意ボックスを表示し、利用規約の免責とも整合させています。

## 3. 同じワークベンチで使う Excel CSV 文字化け修復＆列マスキング

生成AIと並んで現場で毎日起きるのが「UTF-8（BOMなし）の CSV を Excel でダブルクリックして文字化けする」問題です。[Excel CSV文字化け修復（Shift-JIS ⇔ UTF-8 BOM付）＆列マスキング](https://temotobox.com/tools/csv-encoding-fixer/) も、ブラウザ単一タブ内のメモリだけで完結します。

1. **自動文字コード判定＆デコード**: 先頭バイト列から UTF-8 BOM（`0xEF 0xBB 0xBF`）や UTF-16 LE/BE を判定し、それ以外は `encoding-japanese` で Shift-JIS / EUC-JP / JIS / UTF-8 を判別してデコードします。
2. **RFC 4180 準拠の引用符付きパーサ**: セル内の改行・カンマ・エスケープ済みダブルクォート（`""`）を壊さずに二次元配列へ展開し、区切り文字（カンマ / タブ）も自動判定します。
3. **社外提出前の列マスキング＆削除**: AIや外部ベンダーへ共有する前に、「氏名」「メールアドレス」などの特定列だけをワンクリックで `***` にマスク、または列ごと除外した状態で変換できます。
4. **Excel でそのまま開ける UTF-8 BOM 付き出力**: 再シリアライズした文字列の UTF-8 バイト列先頭に `[0xef, 0xbb, 0xbf]` を結合してダウンロード生成するため、日本語 Windows の Excel でも文字化けせずに開けます。
